약 성분과 효능을 넣으면 논문 근거를 모아 검증된 숫자 JSON을 뱉는 Claude Code 플러그인.

문제why this exists

"프롬프트로 막는다"가 안 먹히는 클래스의 버그

LLM에게 논문 초록을 주고 수치를 뽑으라 하면 대부분 맞습니다. 문제는 틀린 경우가 맞은 경우와 똑같이 생겼다는 것입니다.

관측되는 실패

형태가 완벽한 오답"magnesium 500 mg, sleep time +23%" — 문장 구조도, 단위도, 자릿수도 정상. 근데 그 논문엔 23%가 없다. 두 논문의 값이 합쳐졌거나, 유의성이 효과 크기로 승격됐거나.

왜 프롬프트로 안 막히나

검사 주체가 같은 모델"지어내지 마"는 생성 분포를 조금 기울일 뿐 불변식이 아니다. 같은 컨텍스트에서 같은 모델에게 검사시키면, 만들어낸 값도 "그럴듯하다"고 통과시킨다.

이 프로젝트의 주장

LLM은 후보를 만드는 쪽에만 두고, 합격/불합격 판정은 원본을 재조회하는 결정론적 코드가 한다.
둘 사이를 파일로 끊어 두면 그 경계가 실제로 강제된다.

설계 노트

대안으로 검토했다가 버린 것: LLM-as-judge. 초록을 다시 주고 "이 값이 맞냐"고 물으면 통과율이 올라가지만, 틀린 값을 통과시키는 방향으로 올라갑니다. 판정자가 생성자와 같은 실패 모드를 공유하면 앙상블이 아니라 공모입니다.

여기서 결정론적 검사가 가능한 이유는 도메인 특성입니다 — 정답이 외부에 문자열로 존재합니다(PubMed 초록). 부분문자열 검사로 환원되는 문제라면 LLM에게 판정을 맡길 이유가 없습니다.

도메인3분 브리핑

이 표만 알면 코드가 다 읽힙니다

약학 지식은 필요 없습니다. 아래 9개 용어가 코드에 등장하는 전부입니다.

용어한 줄 정의코드에서의 역할
PubMed / E-utilities미국 국립의학도서관 논문 DB와 그 공개 REST API유일한 외부 의존. esearch(검색) / efetch(본문)
PMID논문 고유 ID (정수 문자열)이 시스템의 기본 키. 모든 값이 PMID에 묶임
abstract (초록)논문 요약문 200~300 단어. 전문은 유료인 경우가 많음검증의 정답지. 여기 없는 문자열은 전부 폐기
RCT무작위 대조 시험. 사람을 두 군으로 나눠 실약/위약 비교숫자를 뽑을 가치가 있는 연구 설계
meta-analysis / SR여러 RCT를 통계적으로 합친 상위 근거있으면 "근거 강함" 판정의 조건
MeSHPubMed의 통제 어휘(표준 태그)검색어 정규화 결과에 포함
효과 크기 vs p값얼마나 큰가(value 23.4%, -0.87+unit mmol/L) vs 우연인가 아닌가(p<0.05)이 구분이 게이트 C3의 전부. p값은 효과 크기가 아님
comparator무엇과 비교한 수치인가 — 위약(placebo) / 실약(active) / 복용 전(baseline)같은 "-0.34"라도 기준이 다르면 못 합침
off-target검색엔 걸렸지만 실제 개입 물질이 다른 논문필터링 대상. 다른 물질의 숫자가 섞이는 주 경로
비유로 옮기면 — PMID = 레코드 ID, 초록 = source of truth 문자열, 효과 크기 = 우리가 추출하려는 필드, p값 = 그 필드로 착각되기 쉬운 다른 컬럼. 그게 전부입니다.
산출물 스펙

입력 "마그네슘 수면" 한 줄 → 출력 evidence-pack.json. 논문별로 4개 슬롯이 채워지거나 null이 됩니다.

{
  "schema": "evidence-pack/0.1",
  "topic": "마그네슘 × 수면",
  "tone": "T2",                     // T1 강함 / T2 조건부 / T3 약함·부정
  "papers": [{
    "pmid": "23853635",
    "slots": {
      "effect":     {"value": "17.36", "unit": "min", "verified": true, "quote": "..."},
      "dose":       {"value": "500",   "unit": "mg",  "verified": true,  ...},
      "population": {...},
      "form":       {"value": null, "verified": false, "reason": "not_extracted"}
    }
  }],
  "verification": {"slots_total": 32, "slots_verified": 21, "slots_rejected": 4, ...},
  "warnings": ["..."]
}
null이 정상 출력값입니다. 이 시스템의 유일한 치명적 실패는 "빈 슬롯"이 아니라 "검증 안 된 값이 채워진 슬롯"입니다. 성공률이 아니라 거짓 양성률로 튜닝된 파이프라인.
구조서브에이전트 = 별도 컨텍스트 윈도우

서브에이전트는 스레드가 아니라 프로세스에 가깝다

Claude Code의 서브에이전트는 자기 컨텍스트 윈도우를 갖고 시작해서, 최종 텍스트 하나만 부모에게 반환하고 사라집니다. 공유 메모리 없음, 부모 대화 안 보임.

메인(오케스트레이터)서브에이전트
컨텍스트세션 전체가 누적호출 시 넘긴 프롬프트만 — 부모 대화 접근 불가
반환—최종 텍스트 1개 (여기선 JSON 문자열로 계약)
중간 작업물남음종료와 함께 소멸 (초록 원문 30편이 여기서 사라짐)
도구전부정의에서 제한 — 이 둘은 tools: Bash만
동시 실행1N개 팬아웃 가능 (여기선 최대 8)
--- agents/abstract-miner.md ---
name: abstract-miner
description: PMID 하나의 초록에서 4슬롯을 원문 인용과 함께 추출한다...
tools: Bash              ← curl만 쓰면 됨. Write/Edit는 안 줬다 — 파일 산출을 기대하지 않는다는 신호이지, 강제는 아니다
model: sonnet            ← 판단이 아니라 추출 작업. 상위 모델 불필요
--------------------------------
(본문 = 시스템 프롬프트. 절차·금지사항·출력 스키마·자기점검)
격리가 실제로 사는 이유 — 오염 차단이 아니라 표면 축소
흔한 과장: "서브에이전트를 쓰면 원문이 메인에 안 들어온다." 사실이 아닙니다. miner가 돌려주는 quote는 글자 하나 안 바꾼 원문 문장이고 그대로 메인에 올라옵니다. 그리고 그건 요구사항입니다 — 게이트가 대조할 대상이 없으면 검증이 성립하지 않습니다.
단일 컨텍스트이 구조
메인에 유입되는 원문초록 30편 전문 (수만 토큰)논문당 ≤4문장
출처 귀속없음 — 어느 값이 어느 논문 것인지 모델만 앎(pmid, slot) 쌍에 구조적으로 묶임
검증 가능성불가 — 무엇을 무엇과 대조할지 정의 불가가능 — quote 단위 substring 검사
교차오염논문 A의 dose + 논문 B의 effect 합성 가능miner는 다른 논문을 본 적이 없음
정확한 진술

컨텍스트 격리는 안전장치가 아니라, 검증을 가능하게 만드는 전처리다.
안전장치는 마지막 파이썬 한 개뿐이다.

설계 노트

왜 miner를 논문당 1개로 쪼갰나 — 8편을 한 에이전트에 주면 컨텍스트 안에 8편의 숫자가 공존합니다. 그 상태에서 "논문 3의 dose"를 물으면 모델은 가장 그럴듯한 dose를 고를 수 있고, 그 값은 실재하는 숫자라 사후 탐지가 어렵습니다. 팬아웃은 성능 최적화가 아니라 교차오염 제거가 목적입니다. 부수적으로 8배 빨라지는 건 덤.

비용: 에이전트 8개 × (프롬프트 + 초록 1편). 순차 대비 토큰은 비슷하고 wall-clock만 줄어듭니다. 요금이 아니라 정확도를 사는 구조입니다.

파이프라인P1 → P2 → P3 → P3-1 → P6

경계마다 데이터 형태가 바뀐다

단계 번호가 P1·P2·P3·P6으로 띄엄띄엄한 이유는 P4·P5·P7·P8이 의도적 미구현이기 때문입니다 (반론 수집 / 안전성 / 카피 / 광고법).

왜 파일로 핸드오프하나 — 컨텍스트를 통한 전달이 아니라
1스크립트는 대화를 못 읽는다. 파일이 유일한 입력 경로 — 이게 물리적 제약이자 설계 이점
2검사 대상이 고정된다. 모델이 "요약해서 넘기는" 여지가 사라짐. 디스크에 있는 바이트가 곧 검사 대상
3재현·디버깅이 된다. 게이트가 이상하면 raw_slots.json만 들고 스크립트를 단독 재실행
SKILL.md에 "값을 고치거나 보기 좋게 다듬지 마라"가 명시돼 있습니다. 오케스트레이터가 한 번이라도 손대면 게이트는 "모델이 만든 값"이 아니라 "모델이 만들고 모델이 다듬은 값"을 검사하게 되고, 통과해도 아무것도 보증하지 못합니다.
설계 노트

P1을 서브에이전트로 안 뺀 이유: 사용자 확인이 필요한 유일한 지점이라서. 서브에이전트는 중간에 사람과 대화할 수 없습니다. "검색어가 틀리면 이후 전부가 틀린다"는 성질 때문에 여기만 인라인 + 확인.

meta.json에 "5개 키만 복사, 없는 키는 지어내지 말 것"이라고 못 박은 이유: 오케스트레이터가 scout 반환값을 재구성하기 시작하면 tone_reason 같은 필드가 조용히 창작됩니다. 스크립트는 없는 키를 null로 채우고 진행하므로, 비는 게 낫습니다.

레이아웃플러그인 규약

디렉토리가 계약이다 — 어기면 조용히 무시

Claude Code 플러그인은 정해진 위치만 스캔합니다. 잘못 두면 에러 없이 로드가 안 됩니다. 이 클래스의 실패는 디버깅 비용이 큽니다.

pubmed-evidence/                          ← 플러그인 루트 = ${CLAUDE_PLUGIN_ROOT}
├── .claude-plugin/
│   ├── plugin.json                     매니페스트
│   └── marketplace.json                로컬 설치용 등록 정보
├── skills/pubmed-evidence/
│   ├── SKILL.md                    frontmatter(name/description) + 절차 본문
│   ├── references/normalize.md         지연 로드. 본문에서 참조할 때만 읽힘
│   └── tests/fixtures.md
├── agents/                             ← 루트여야 스캔됨. skills/ 하위는 무시
│   ├── evidence-scout.md
│   └── abstract-miner.md
└── scripts/
    ├── verify_evidence.py              stdlib only, no deps
    └── test_verify_evidence.py          assert 스크립트. 프레임워크 없음
규칙이유 / 실패 양상
agents/는 플러그인 루트스킬 폴더 하위는 스캔 대상이 아님 → 에이전트가 존재하지 않는 것처럼 동작. 가장 흔한 삽질
scripts/ 참조는 ${CLAUDE_PLUGIN_ROOT}상대경로는 사용자 CWD에 따라 깨짐. 절대경로는 배포 불가
references/는 스킬 하위SKILL.md 본문이 참조할 때만 읽힘 = 컨텍스트 지연 로딩

프롬프트를 룰 엔진처럼 쓴다

이 에이전트가 하는 일은 분류와 선별뿐입니다. 수치 추출은 명시적으로 금지 — 책임이 겹치면 어느 쪽이 틀렸는지 특정할 수 없습니다.

쿼리 4개, 각각이 하나의 판정 입력
#필터산출하는 사실
1meta-analysis[pt] OR systematic review[pt]상위 근거 존재 여부
2randomized controlled trial[pt] AND humans[mh]채굴 후보 확보
3humans[mh]만인체 연구 자체가 0인가
4guideline[pt] OR practice guideline[pt] OR consensus...guideline_hit 불리언
4번을 빼면 R1이 절대 발화하지 않습니다. T1의 조건이 상위근거 positive AND guideline_hit이므로, 입력이 항상 false면 근거가 아무리 강해도 T2로 떨어집니다. 실제로 픽스처 F1이 계속 T2로 나왔던 원인이고, 지금은 회귀 테스트 항목으로 박혀 있습니다.
쿼리 설계 = 판정 로직. "검색을 몇 번 던지는가"가 상태 머신의 입력 개수를 정합니다. 이 매핑을 프롬프트에 표로 넣어두면 모델이 임의로 합치지 않습니다.
순서가 있는 규칙 — first-match-wins
R1. MA/SR ≥1 positive AND guideline_hit        → T1
R2. MA/SR ≥1 negative OR (RCT≥3 중 positive < 1/3)  → T3
R3. 인체 RCT == 0 (animal/in-vitro만)          → T3
R4. positive지만 subgroup 한정 OR 혼재         → T2
R5. otherwise                                  → T2 (보수적 기본값)

// 반환에 tone_reason: "R4: RCT 5편 중 3편 positive이나 모두 결핍군 한정"
// → 어느 규칙이 발화했는지가 출력에 남는다. 디버깅과 회귀 판정의 근거
기본값이 T2(보수)이고, 규칙 순서상 T3가 T2보다 먼저 검사됩니다. "판정 불가"를 낙관 쪽으로 흘리지 않으려는 배치입니다.
프롬프트에 "T3로 판정하는 것을 두려워하지 마라"가 명시돼 있습니다. sycophancy 대응 — 모델은 요청자가 원할 법한 결론(근거 있음)으로 기웁니다. 기본값·규칙 순서·명시적 문장 세 겹으로 눌러놨고, 그래도 못 믿어서 픽스처 F4로 상시 감시합니다.
off-target 필터 — 도메인 지식이 코드가 아니라 데이터에 있다

"EPA"로 검색하면 크릴오일·EPA+DHA 복합제·ALA 비교시험이 함께 걸립니다. 서로 다른 물질의 수치가 한 결과 집합에 섞이면 그 팩은 통째로 폐기 대상입니다.

설계 노트

스키마가 신뢰 표면을 정한다

추출기 하나에 논문 하나. 핵심은 반환 스키마입니다 — 모든 값이 자기 근거 문장을 데리고 다니게 만들어 놓으면, 다음 단계가 순수 문자열 검사로 끝납니다.

슬롯 계약: {value, unit, quote}
quote ⊂ 초록, value ⊂ quote, unit ⊂ quote — 전부 문자 그대로
이 세 관계가 성립하면 검증이 substring 문제로 환원됩니다. LLM의 판단을 신뢰할 필요가 없어지는 지점이 여기입니다.
// 초록: "...decreased sleep onset latency by 17.36 min (P = 0.02)."

OK  {"value":"17.36", "unit":"min", "quote":"decreased sleep onset latency by 17.36 min (P = 0.02)."}

NG  {"value":"17.36", "unit":"hours"}   ← 값은 통과, 단위만 창작 = 60배. C4가 잡는다
NG  {"value":"약 17분"}                ← 변환 + 번역
NG  {"value":"17"}                     ← 반올림
NG  {"unit":"mg/day"}                 ← 초록이 "500 mg ... daily"면 unit은 "mg". 표준형 변환 금지
value/unit 분리는 그 자체로 취약점을 만듭니다. value만 검사하면 unit 필드는 무검증 자유 텍스트가 되고, 카드에 렌더링되는 건 둘의 결합입니다. 스키마를 쪼갤 때마다 검사도 같이 쪼개야 한다는 일반 교훈.
effect 슬롯 — 타입은 맞는데 의미가 틀린 값

effect = 효과 크기

"얼마나 큰가" — value는 숫자 하나(부호·소수점·천단위·%까지). 단위는 unit, 지표명(RR·OR·HR·SMD·MD)은 measure로 갈라 담는다

effect ≠ 유의성 → null

"우연인가 아닌가"p < 0.05 · 95% CI 0.12 to 0.48 (점추정치 없음) · significantly reduced

"p < 0.05"는 초록에 실재하는 문자열입니다. quote ⊂ 초록, value ⊂ quote를 전부 만족합니다. 즉 C1·C2를 정상 통과하는 오답이고, 이것 때문에 C3라는 별도 형태 검사가 존재합니다.

검증할 수 없는 필드는 신뢰 목록에서 뺀다.
unit_type은 값에서 재계산하고, comparator·measure는 enum 밖이면 null로 떨어뜨린다.
"모델이 준 값을 그대로 쓰는 필드"를 최소화하는 것이 스키마 설계의 목표.

self-check 5문항 — 출력 직전 강제
1quote가 초록에 있는가 → 아니면 슬롯 null
2value가 quote에 있는가 → 아니면 슬롯 null
3unit이 quote에 있는가 → 아니면 unit만 null (표준형으로 채우지 말 것)
4숫자·단위를 변형했는가 → 되돌림
5effect가 p값·CI·서술어뿐인가 → 슬롯 통째로 null

# 이전: 걷어내기 방식. p값·CI 패턴을 지우고 남는 숫자가 있으면 통과
# → "P for trend = 0.03" 같은 새 표현마다 구멍이 생겼다 (실측 6건 통과)

EFFECT_VALUE = re.compile(r"^-?\d+(?:,\d{3})*(?:\.\d+)?%?$")  # 지금: 숫자 하나 형태만 허용

def effect_shape_reason(value_norm):
    if EFFECT_VALUE.match(value_norm):
        return None              # 통과 — 판정은 여기서 끝난다
    # 여기부터는 이미 폐기 확정. P_TOKEN/CI_TOKEN은 이제 판정에 안 쓰이고,
    # 사람이 읽을 폐기 사유 라벨을 고르는 데만 쓰인다
    if not HAS_DIGIT.search(value_norm):
        return "no_numeric_effect"
    if HAS_DIGIT.search(P_TOKEN.sub(" ", CI_TOKEN.sub(" ", value_norm))):
        return "effect_value_not_numeric"   # 숫자는 있는데 다른 게 섞임 — "RR 0.78" 같은 프로즈
    if P_TOKEN.search(value_norm):  return "p_value_not_effect_size"
    return "ci_only_not_effect_size"

왜 뒤집었는가 — 막을 것을 열거하면 표현이 늘 때마다 구멍이 생기고, 허용할 것을 열거하면 끝난다. 이전 버전은 P_TOKEN·CI_TOKEN을 걷어낸 뒤 남는 숫자를 효과 크기로 인정하는 블랙리스트였는데, "P for trend = 0.03" 같은 새 표현이 나올 때마다 뚫렸다(실측 6건). EFFECT_VALUE는 "숫자 하나"라는 닫힌 형태를 정의하므로, 자연어 표현이 아무리 늘어도 구멍이 생기지 않는다.

measure 필드가 신설된 것도 같은 이유다. RR 0.78을 통째로 value에 허용하면 화이트리스트가 프로즈를 받아들여야 하고, 그 순간 "p for trend = 0.03"도 같이 들어온다. 지표명은 measure(RR/OR/HR/SMD/MD 열거값만) 칸으로 분리해 value가 "숫자 하나"라는 형태를 유지하게 했다.
P_TOKEN 자체의 함정은 그대로 남아 있다 — (?<![a-z])가 없으면 "sbp -5.2", "sleep -1.2"의 끝 p가 p값으로 오인됩니다(문자 클래스의 하이픈이 음수 부호를 먹음). 이제는 판정을 좌우하지 않지만, 폐기 사유 라벨이 틀리면 디버깅이 늦어진다는 점은 여전합니다.

def normalize(text):
    t = unicodedata.normalize("NFKC", text)
    t = t.translate(DASHES).translate(QUOTES).translate(DQUOTES)  # – — ' " 통일
    t = re.sub(r"\s+", " ", t)
    return t.strip().lower()
# 숫자·단위는 절대 건드리지 않는다 — 그걸 검사하는 게 목적이므로
정규화는 거짓 폐기를 줄이려고 있습니다(PubMed XML의 유니코드 대시 vs 에이전트가 옮겨 적은 ASCII 하이픈). 여기에 "숫자 반올림 허용" 같은 걸 넣는 순간 게이트는 무의미해집니다. 흡수 범위를 넓히자는 요청이 오면 그건 게이트를 약화시키자는 요청입니다.

    if len(kinds) > 1:
        warnings.append(f"effect {label}이 논문마다 다르다 ... 슬라이드를 나눌 것")

개별 값은 전부 검증을 통과했는데 집합으로 모으면 틀리는 케이스입니다(%와 절대량 혼재, 위약 대비와 복용 전후 혼재). 슬롯 단위 검사로는 안 잡히므로 팩 단위 후처리로 경고를 답니다.

이 파일 한 줄 요약

LLM은 후보 생성기,
합격 판정은 원본을 재조회하는 코드

경계를 파일로 끊고, 판정 함수는 순수하게 유지하고, 그 함수에만 테스트를 붙인다. 나머지는 전부 "제안"이다.

테스트확률적 시스템을 어떻게 검증하나

두 층으로 나눠서 잰다

전체 파이프라인은 결정론적이지 않습니다. 그래서 결정론적인 부분은 단위 테스트로, 확률적인 부분은 판정 회귀로 나눠서 봅니다.

층 1 — 게이트 단위 테스트 (결정론)

test_verify_evidence.py네트워크 없이 verify_slot()만 호출. assert 기반 스크립트 한 장, 프레임워크 없음. 1초, 항상 같은 결과.

층 2 — 판정 회귀 (확률적)

fixtures.md 4케이스실제 PubMed에 붙여 tone·needs_decomposition만 검사. 수치는 검사 안 함 (DB가 변하므로). 3회 중 2회 일치면 통과.

층 1 — 문서에 적힌 금지 문자열이 곧 테스트 케이스
python3 scripts/test_verify_evidence.py   # → ok

# 케이스 출처 규칙: abstract-miner.md의 "넣으면 안 되는 것" 목록에 있는 문자열은
# 하나도 빠짐없이 테스트에 있어야 한다. 구현을 보고 테스트를 쓰지 않는다.
"p < 0.05" / "P-value = 0.03" / "significant at p<0.001" / "(95% CI 0.12 to 0.48)"
"significantly reduced" / "17.36"+"hours" / comparator="vs. usual care" → null
"sbp -5.2" / "-0.34"+"mmol/L" / dose "500 mg"                            → 통과
거짓 폐기(정상 값을 버리는 쪽) 케이스가 절반입니다. 게이트를 조이는 커밋마다 이쪽이 먼저 깨집니다 — "sbp -5.2"가 그 감시 케이스.
층 2 — 4개 픽스처가 지키는 것
ID입력기대회귀로 잡는 것데모
F1오메가3 중성지방T1 / decomp true4차(guideline) 쿼리 누락 — 빠지면 영원히 T2→ P2에서 멈춤 (decomp true)
F2마그네슘 수면T2 / false기준선✅ P1→P6 전 구간
F3유산균 IBST2 / true룩업 테이블의 decompose_default 미조회→ P2에서 멈춤 (decomp true)
F4콜라겐 피부탄력T3 / falsesycophancy 회귀. T1/T2로 뜨면 릴리스 불가톤(T3) 시연용. 채굴 대상 적어 exit 2로 끝날 수 있음
경계 흔들림 허용 범위를 문서에 명시해뒀습니다 — F1(T1↔T2), F2(T2↔T3)는 허용, F4는 불허. 확률적 시스템의 회귀 테스트는 어디까지 흔들려도 되는지를 같이 적어야 운영됩니다.
needs_decomposition: true인 F1·F3는 P2에서 멈춘다 — 사용자에게 하위 분해 여부를 되묻는 지점이 파이프라인의 끝이다. P1→P6 전 구간(파일 저장·검증까지)을 보여주는 라이브 데모는 F2를 쓴다.
구조 검증 항목도 픽스처에 있습니다: scout 출력에 인용문·수치가 없을 것, miner의 모든 value가 quote의 부분문자열일 것, raw_slots.json·meta.json이 파일로 저장될 것, 존재하지 않는 PMID에 error: fetch_failed를 반환할 것.
설계 노트

층 1은 CI에 넣을 수 있고, 층 2는 못 넣습니다(네트워크 + 비결정성 + 비용). 대신 층 2는 릴리스 체크리스트로 운영합니다. LLM 파이프라인에서 "테스트가 다 초록불"이 의미하는 범위를 정확히 좁혀두는 게 중요합니다 — 초록불이 보장하는 건 게이트가 안 뚫렸다는 것뿐입니다.

이식다른 도메인으로 옮길 때

약학을 걷어내고 남는 일반형

이 구조는 "외부에 정답 문자열이 존재하는 추출 작업"이면 그대로 옮겨집니다. 계약서 조항 추출, 재무제표 수치 파싱, 로그에서 인시던트 타임라인 뽑기, 코드베이스 감사 등.

1추출값마다 근거 문자열(quote)을 강제한다. 이게 없으면 이후 전부가 불가능. 스키마 레벨에서 필수 필드로
2검증은 소스를 재조회해서 한다. 모델이 넘긴 소스로 대조하는 건 같은 출처를 두 번 믿는 것
3단위로 쪼갠 팬아웃. 문서 N개 = 에이전트 N개. 한 컨텍스트에 여러 소스를 넣으면 합성이 일어나고, 합성된 값은 사후 탐지가 어렵다
4파일로 핸드오프. 모델과 검사기 사이를 디스크로 끊으면 "요약해서 넘기기"가 물리적으로 불가능해진다
5검증 못 하는 필드는 신뢰 목록에서 뺀다. 값에서 재파생하거나(unit_type), enum으로 강등하거나(comparator), 아예 받지 않는다
6실패를 등급화한다. 필드만 버림 / 레코드 버림 / 결과 전체 불신(exit 2). 전부 같은 등급으로 처리하면 과폐기 아니면 과통과가 된다
7모델의 낙관 편향에 기본값으로 대응한다. 판정 규칙 순서, 보수적 기본값, 명시적 "약하게 나와도 된다" 문장, 그리고 그걸 감시하는 회귀 케이스
8집합 수준 검사를 따로 둔다. 개별 값은 다 맞는데 나란히 놓으면 틀리는 경우(축·기준 불일치)는 슬롯 검사로 안 잡힌다
옮기면 안 되는 경우: 정답이 외부 문자열로 존재하지 않는 작업(요약, 카피라이팅, 판단). C1이 성립하지 않으므로 이 구조의 이점이 전부 사라집니다. 그래서 이 플러그인도 카피 작성(P7)은 범위 밖으로 잘라냈습니다.
설계 노트

가장 이식성 높은 조각은 의외로 6번(실패 등급화)입니다. 대부분의 "LLM 검증 레이어"는 통과/실패 2단계로 시작했다가, 과폐기 때문에 임계값을 낮추고, 결국 게이트가 무력해지는 경로를 밟습니다. 실패 종류마다 죽이는 범위를 다르게 두면 임계값을 안 낮추고 버틸 수 있습니다.

알려진 한계 · 이 구조가 보장하지 않는 것

① quote는 메인 컨텍스트에 들어온다. 격리는 오염 차단이 아니라 표면 축소다. 최종 보증은 게이트 하나에서 나온다
② 초록만 본다. 본문에만 있는 수치는 구조적으로 못 뽑는다 — null이 되고, 그게 의도된 동작이다
③ comparator는 검증 불가. 문장이 아니라 판정이라 substring 검사가 성립하지 않는다. enum 밖이면 null로 떨어뜨리는 게 최선
④ tone 판정은 확률적이다. 검색 시점 논문 수에 따라 경계에서 흔들린다. 흔들림 허용 범위를 문서에 명시하고 F4만 불허로 고정
⑤ 게이트는 "원문에 있음"만 보장한다. 그 값이 해당 슬롯에 적절한지(dose 칸에 age를 넣었는지)는 C1–C4로 안 잡힌다
⑥ P8(광고법 검사) 미구현. 출력물을 그대로 발행하면 안 된다 — 팩의 warnings에 항상 이 문장이 박힌다
