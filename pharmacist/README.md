# pharmacist — 약사 대상 AI 스터디 자료

건강기능식품 콘텐츠를 만드는 실제 업무를 AI 에이전트로 옮긴 세 갈래 실습이다.
각각 다른 질문에 답한다.

| 디렉토리 | 한 줄 | 배우는 것 |
|---|---|---|
| `ingredient-analysis/` | 성분 하나로 상품 문구를 뽑는 파이프라인 | 서브에이전트 분업·도구 제약·파일 인계 |
| `kr-claims/` | 식약처 고시 대조 (공용 도구) | 결정론적 게이트 — LLM에 맡기면 안 되는 판정 |
| `evidence-card/` | PubMed 근거 수집·검증 플러그인 | 숫자 환각 차단, 플러그인 배치 |

세 개가 한 흐름으로 이어진다.

```
성분 × 증상
   │
   ├─ evidence-card ──→ evidence-pack.json   "이 숫자가 그 논문에 실재하는가"
   │                          │
   │                          ↓
   ├─ kr-claims ──────→ kr-report.json       "이 숫자를 국내에서 써도 되는가"
   │                          │
   │                          ↓
   └─ ingredient-analysis ─→ copy/{성분}-v3.md   "그래서 뭐라고 쓸 것인가"
```

---

## ingredient-analysis/ — 서브에이전트 파이프라인

조사 → 카피 → 검수 → 수정을 **각각 다른 담당(서브에이전트)** 에게 맡기고,
메인 에이전트는 검증과 판정만 한다. `/성분조사 {성분명}` 하나로 돈다.

```
ingredient-analysis/
├── .claude/
│   ├── skills/
│   │   ├── 성분조사/SKILL.md      0~4라운드 파이프라인 + 종료 판정 규칙
│   │   └── sag/SKILL.md           위임 자체의 규칙 (지시문·병렬·검증)
│   └── agents/
│       ├── researcher.md          웹 검색 O · 쓰기 O
│       ├── copywriter.md          웹 검색 X · 읽기/쓰기만
│       ├── reviewer.md            쓰기 X — 지적만 반환 (모델: opus)
│       └── chief.md               쓰기 X — 흩어진 결과 종합
├── research/{성분}-고시.json      0라운드 산출물 (메인이 kr-claims에서 뽑는다)
├── research/{성분}.md             1라운드 산출물
├── copy/{성분}-v1~v3.md           2·4라운드 산출물
└── review/{성분}-v1-검수.md       3라운드 산출물 (메인이 저장)
```

산출물 디렉토리는 실행하면 생긴다. **고시 원문은 이 디렉토리에 두지 않는다** —
고시에서 오는 값은 전부 `kr-claims/data/kr_claims.json`을 거쳐 0라운드로 들어온다.

### 구조가 이렇게 생긴 이유

- **메인은 끝까지 살아 있고, 담당은 생겼다 사라진다.** 담당이 웹 스무 장을 읽어도
  메인에는 요약 한 덩어리만 돌아온다. 안 나누면 메인 컨텍스트가 금방 찬다.
- **담당끼리 대화하지 못한다.** 문구 담당은 조사 담당을 만난 적이 없다.
  `research/`, `copy/`, `review/` 파일이 유일한 통로다 — 담당이 사라져도 파일은 남는다.
- **도구를 안 준 것이 견제다.** 검수 담당에게 쓰기 권한이 없으므로 검수가 원고를
  직접 고치는 일이 일어날 수 없다. 부탁이 아니라 설정이다.
- **담당은 전부 `Bash`가 없다.** 고시 조회(0라운드)·파일 변환 같은 시스템 작업은
  메인 몫이다. 메인이 `kr-claims`로 **해당 원료만** 뽑아, 인정 문구를 한 글자도
  다듬지 않고 담당에게 넘긴다. 13만 자 JSON을 담당에게 통째로 읽히지 않는다.

### 메인이 하는 네 가지

1. 담당 결과를 **원본과 대조해 검증** (자기보고를 믿지 않는다)
2. 「확인 필요」 중 담당이 도구가 없어 못 푸는 것을 처리
3. 다음 담당에게 필요한 정보를 파일 경로로 인계
4. 종료 판정 — 「지적 0건」을 목표로 하면 끝나지 않는다

## kr-claims/ — 식약처 고시 대조 (공용)

「건강기능식품의 기준 및 규격」 고시전문에서 **인정 기능성 문구**와 **일일섭취량**을
추출해 두고, 콘텐츠마다 대조한다. `evidence-card`와 `ingredient-analysis` 양쪽이
호출하므로 스크립트는 여기 한 벌만 둔다.

```
kr-claims/
├── scripts/
│   ├── build_kr_claims.py     raw/고시전문.txt → kr_claims.json (개정 시에만)
│   ├── check_kr_claims.py     조회 / 대조 (콘텐츠마다)
│   └── test_kr_claims.py      네트워크 없이 도는 계약 검사
├── data/kr_claims.json        원료 97개 · 행 120개 — 저장소에 남는 유일한 고시 자료
├── raw/                       고시 원문. 빌드할 때만 생긴다 (git 미추적)
└── README.md                  취득 절차 + 두 게이트 역할 분담
```

키는 **(원료 × 기능성)** 이다. 같은 원료라도 기능성마다 섭취량이 다르게 고시돼 있어서,
원료당 하나로 저장하면 중성지질 콘텐츠에 기억력 기준이 붙는다.

**원문은 남기지 않고 JSON만 남긴다.** 27만 자짜리 txt가 저장소에 있으면 에이전트가
그쪽을 직접 읽고, 파싱·검증을 거치지 않은 값이 콘텐츠로 흘러든다. 입구를 하나로 막는다.
대신 JSON에 담기는 것은 인정 문구·일일섭취량·주의사항뿐이다 — 총론, 규격, 원료 목록은
없으므로 그게 필요하면 **사람이 고시 원문을 봐야 한다.**

**LLM이 아니라 스크립트다.** 상한 초과면 종료 코드 2로 발행을 막는다.
판정 근거가 매번 같아야 하는 일은 모델에 맡기지 않는다.
자세한 절차와 한계(미등재 ≠ 인정되지 않음)는 `kr-claims/README.md`에 있다.

## evidence-card/ — 근거 수집·검증 플러그인

성분 × 효능 조합의 PubMed 근거를 모아 `evidence-pack.json`을 만들고,
초록에 실재하지 않는 숫자를 스크립트 게이트로 걸러낸다.
구조와 실습 절차는 `evidence-card/README.md` 참고. *(정리 중 — 확정 후 이 절 보강)*

---

## 두 게이트는 서로를 대신하지 못한다

| | evidence-card | kr-claims |
|---|---|---|
| 묻는 것 | 이 숫자가 그 초록에 실재하는가 | 이 숫자를 국내에서 써도 되는가 |
| 기준 | PubMed 초록 | 식약처 고시 |
| 실패 형태 | 환각·조작 | 광고법 위반·용량 일탈 |

근거 검증을 통과한 500 mg이 고시 상한(250 mg) 초과로 걸리는 것이 정상 동작이다.

## 공통 전제

- **문구가 완성돼도 게시 가능 상태가 아니다.** 사전 자율심의, 품목제조신고번호,
  판매업 신고, 게시 직전 현행 고시 재확인이 남는다. 전부 사람(약무) 영역이다.
- 고시 기준 시점은 **2026.6.11(제2026-43호)** 이다. 개정되면
  `kr-claims/README.md`의 1·2절을 따라 `kr_claims.json`을 다시 만든다.
- 스크립트는 Python 3만 있으면 돈다. 회귀 테스트는 네트워크가 필요 없다.
